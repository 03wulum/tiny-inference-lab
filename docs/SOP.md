# Experiment SOP v0.7

> Copy of the living SOP doc (https://claude.ai/artifact/BfqrH1AaWwEYeSweLHmsCF). Changes go through a `sop/<what>` PR that edits this file, with a version bump and a changelog line. Other topic repos copy this file and note the version.

Every experiment is a small, honest, one-command test of a recent paper's claim. Training runs on Fortran's NVIDIA GPU, evaluation runs anywhere, and its pass/fail criteria are fixed before any code is written. One theme runs through all of it: how much intelligence fits in very little space.

## 1. Principles

- **Small is the point.** Size is a first-class variable. Every experiment declares a disk and RAM budget and asks how close a tiny version gets to a big one: can 100 MB match what 500 MB to 1 GB does, and where does it break?
- **Decided up front, judged by tests.** The hypothesis and pass criteria are written before coding. The suite prints PASS or FAIL per criterion and an overall verdict. Thresholds never move after results come in.
- **Done together.** Obi sees the plan before the build and gets a plain-language explainer after it. Anything Obi could be asked about in public, Obi understands.
- **Obi decides what goes public.** Claude gives a post-readiness verdict and a draft post. Obi chooses whether and when to post.
- **Clean and contained.** The PC is shared with other agents, so experiments stay small, self-contained and safe (§7).
- **Few repos, many experiments.** A handful of topic repos, each holding numbered experiments and one run-all.

**Proceed by default.** Once Obi has picked a project, threads don't ask for permission. They run each step and report what they did, since nearly everything can be rolled back. They stop and ask only before a critical or irreversible step: deleting Obi's own files or data outside the experiment, posting anything publicly on Obi's behalf, spending money, or changing anything outside the project.

## 2. Naming

- **Topic repo:** `<topic>-lab`, public, MIT, under `03wulum`. Aim for about five in total. A new topic repo needs a theme that will hold at least three experiments; otherwise the experiment goes into the closest existing repo.
- **Experiment folder:** `experiments/NN-short-slug/`, numbered in creation order, never renumbered. A follow-up says what it builds on ("builds on 01").
- **Branch:** `exp/NN-short-slug` for an experiment, `fix/<what>` or `sop/<what>` otherwise.

## 3. Repo layout

```
<topic>-lab/
  README.md          Results table first (§6), then the index
  run_all.py         runs every experiment (--quick by default) and prints one verdict table
  requirements.txt   shared deps, exact pins
  LICENSE  .gitignore  .github/workflows/ci.yml
  docs/SOP.md        copy of this SOP, with its version
  experiments/NN-short-slug/
    README.md        short public write-up (§6)
    EXPLAINER.md     plain-language explainer for Obi (§9)
    criteria.py      hypothesis, pass criteria, controls, size budget, as code (§4)
    train.py         GPU training, saves checkpoints (only if the experiment trains)
    run.py           entry point: --quick, --seed, --clean; prints the PASS/FAIL table
    <method>.py      the implementation, importable, no side effects
    test_<method>.py code-correctness tests, < 10 s
    results/         results.md, verdict.json, *.png, all generated by run.py
    docs/            optional: method, controls, full tables
```

Run everything with `python run_all.py` (add `--full` for full runs), or one experiment with `python run.py` from its folder. Notebooks are never the source of truth. Weights and datasets are never committed (§7).

## 4. Hypothesis, pass criteria and controls

Before any code, the thread writes this plan, publishes it (plan doc and `criteria.py`) and posts it to Obi. It then starts building without waiting for approval. Obi can redirect at any time, and any change to the criteria is logged with its reason.

1. **Hypothesis:** one sentence with a number, e.g. "3-bit TurboQuant keeps attention KL below 0.2 on an outlier-heavy KV cache at 5x less memory than fp16."
2. **Pass criteria:** 2 to 5 measurable checks, each with a metric, a threshold and the setup (data, size budget, seeds). Thresholds come from the paper or the baseline, never from our own results.
3. **Assumptions:** listed, and kept as few as possible.
4. **Controls:**
    - **Baseline:** what practitioners use today, at the same memory or compute.
    - **Negative control:** break the mechanism on purpose (skip the key step, shuffle labels, random weights). The criteria should now FAIL. If they still pass, the test proves nothing.
    - **Perturbations:** tweak the inputs (other sizes, seeds, noise, out-of-distribution data, smaller budgets) and record which criteria still pass. That map is the analysis.

`run.py` prints one table, criterion · value · threshold · PASS/FAIL, for the main run and each control, then an overall verdict, also written to `results/verdict.json`:

| Verdict | Meaning |
| --- | --- |
| PASS | All pre-registered criteria pass and the negative control fails |
| FAIL | The core criterion fails |
| INCONCLUSIVE | Mixed results, or the negative control passed so the test can't tell |
| ✨ INTRIGUING (optional tag) | Added beside any verdict when something unexpected turned up or results beat expectations, with a one-line note. It never changes the verdict |

Two layers, kept apart: `pytest` checks that the code is correct and must always be green. The verdict checks the paper's claim, and FAIL is a valid result that does not break CI. CI fails only on a failing code test, a crash, or a blown budget.

## 5. Reproducibility and budgets

- **One command:** `python run.py` reproduces every number and plot. `--quick` finishes in under 30 s and is what CI and `run_all.py` use.
- **Size budget:** declared in `criteria.py` and measured by `run.py` (peak RAM, bytes on disk for models and data). Defaults: peak RAM ≤ 2 GB; everything kept (trained models, checkpoints) ≤ 50 MB combined, and ≤ 20 MB for the learn-while-prompted line; temporary downloads ≤ 2 GB per experiment, deleted by `--clean` when done. Big reference models are compared by their published scores, never downloaded.
- **Training:** ≤ 15 minutes per experiment (20 at most), inside the size budget. Training never runs on CPU: it runs on Fortran's NVIDIA GPU through Remote Control and uses as much free GPU capacity as is available (largest batch that fits, mixed precision) to cut the time. Every experiment uses the GPU for at least some of its work. `train.py` saves checkpoints, so `run.py --quick` and CI only load them and evaluate. The aim is training and inference that both finish in minutes.
- **Seeds:** `--seed`, default 0, recorded in results. Separate RNG streams for data and for the method's own randomness. Headline comparisons report mean ± std over at least 3 seeds.
- **Pins:** exact `==` versions, Python version stated (currently 3.12), Hugging Face models pinned to a revision hash.
- **results.md header:** seed, quick flag, runtime, peak RAM, disk used, Python and library versions, CPU/GPU model.

## 6. READMEs

READMEs are short and lead with what happened. Detail goes into each experiment's own docs (`EXPLAINER.md`, `results/results.md`, and the optional `docs/` folder).

**Top-level repo README:** a `## Results` section right under the one-line intro, one row per experiment:

```markdown
## Results
| # | Goal | Verdict | Criteria | Finding in one line | |
| 01 | Shrink the KV cache 5x with no calibration | PASS | 3/3 | Attention KL 0.15 vs 0.49 for the usual method | [details](experiments/01-.../) |
| 02 | Exponential gains from swarms of tiny models | FAIL ✨ INTRIGUING | 3/5 | Gains follow a power law; diversity, not count, drives them | [details](...) |
```

**Experiment README:** opens with the goal in one line, then the verdict (PASS, FAIL or INCONCLUSIVE, plus any ✨ INTRIGUING note), then a Details link, then the PASS/FAIL table. A reader knows in ten seconds what happened. Keep it to about one screen on a phone.

```markdown
# NN · <Method>: <one-line claim in plain words>

**Goal:** one line. **Verdict:** PASS / FAIL / INCONCLUSIVE (+ ✨ INTRIGUING note). [Details](docs/)

**Paper:** Authors. *Title.* [arXiv:XXXX.XXXXX](link), venue year.
**Why it matters on-device:** one or two sentences on memory, latency, battery or offline use.
**Size budget:** peak RAM, disk.

## Pass criteria
| # | Criterion | Threshold | Result | PASS/FAIL |

## Controls
Baseline, negative control, and which criteria survived each perturbation.

## What I found that the abstract doesn't tell you

## Run it
python run.py           # ~Ns
python run.py --quick   # ~Ns
python -m pytest -q

## Limitations and next steps
```

The README states the hardware the timings came from.

## 7. Safety, footprint and cleanup

- Install only into the repo's own `.venv`. Never `sudo`, system-wide `pip`, or `curl | sh`.
- Use well-known packages from PyPI, with exact pins. Every new dependency gets a one-line reason in the PR.
- Download models and data only from open-licensed sources (Hugging Face, PyPI, the paper's official release; Apache, MIT, CC-BY or similar), at a pinned revision, with the size checked before downloading, and never run downloaded code (`trust_remote_code=False`).
- Everything downloaded goes into a git-ignored `data/` folder.
- Never write outside the repo and never leave background processes running.

**Cleanup when an experiment is done.** Nothing piles up on Fortran. After the final run, `python run_all.py --clean` (or `python run.py --clean` in one experiment) deletes temporary downloads, datasets, caches (pip, Hugging Face, torch), the experiment's `.venv` and intermediate checkpoints. Only the committed ≤ 50 MB artifacts and `results/` stay. The command prints the disk space it freed, and that number goes in the PR and the thread's final report.

## 8. Results and plots

- Tables in `results/results.md`; the README copies only the headline table.
- Plots: PNG, matplotlib, 150 dpi, readable on a phone (labels ≥ 11 pt, one message per plot, title states the takeaway, units on axes). Baseline in gray, the paper's method in one accent color.
- Where size is the variable, plot quality against size, with the budget line marked.
- Report negative or surprising results plainly. A FAIL with a good explanation is a portfolio asset.

## 9. Explainer for Obi

`EXPLAINER.md`, readable on a phone in about 5 minutes, every term defined on first use:

1. What we tested and why, in two sentences.
2. How the method works, with an analogy.
3. The process step by step, and the choices made where Obi might disagree.
4. What we found, including what failed.
5. Why it matters: real-world uses (phones, laptops, offline agents) and who cares.
6. The broader conversation: 3 to 5 links (the paper, related work, critiques, talks) for deeper reading.
7. Questions someone might ask Obi about it, with short answers.

## 10. Post-readiness

Every finished experiment ends with one verdict from Claude:

- **Post now:** verdict settled, controls run, plots clean, explainer done.
- **Needs more:** what is missing, e.g. real model data instead of synthetic.
- **Defer:** the result is too thin or not new.

It comes with a draft post of up to 280 characters: the finding with its number, the paper, the repo link, and the plot to attach. Obi decides and posts; Claude never posts.

## 11. Commits and PRs

- Conventional commits: `exp(01): ...`, `fix(01): ...`, `docs: ...`, `ci: ...`, `sop: ...`.
- One experiment per PR, titled `Experiment NN: <method> (<verdict>)`.
- PR body: paper link, the criteria table with the verdict, runtime and size, limitations, post-readiness and the draft post.
- `main` always runs. The same PR updates the repo README Results table, the project index (§16) and `run_all.py`.

## 12. Per-experiment checklist

- [ ] Paper picked; plan (hypothesis, criteria, controls, size budget) published and sent to Obi before coding (no waiting)
- [ ] Folder with the standard files, including `criteria.py`
- [ ] Baseline, negative control and perturbations implemented
- [ ] `pytest` green; `run.py` prints the PASS/FAIL table and writes `verdict.json`
- [ ] Inside the runtime and size budget, measured; training on GPU only
- [ ] Results and plots generated by `run.py`
- [ ] README (goal, verdict, details link first) and EXPLAINER written
- [ ] Added to `run_all.py`, the README Results table and the project index
- [ ] CI green; PR opened with the standard title and body
- [ ] Post-readiness verdict and draft post sent to Obi
- [ ] Cleanup run on Fortran (`--clean`); disk space freed reported to Obi

## 13. Creating a new repo

Cloud threads cannot create GitHub repos. Every new repo is made on Obi's Windows PC "Fortran" with `gh`, signed in as the existing `03wulum` account, one repo per topic.

1. **Request:** the thread that needs a repo asks the coordinator, or messages the thread "Set up repo creation from my computer", with the name `<topic>-lab`.
2. **Create:** that thread runs `gh repo create 03wulum/<topic>-lab --public`. The repo starts empty, with no README.
3. **Approve:** no separate approval is needed once Obi has picked the project. The repo-creation thread creates it and reports back.
4. **Wire up:** the requesting thread adds the repo to its workspace and scaffolds the layout in §3 including `docs/SOP.md`, and pushes on a branch with a PR.

On a phone, Obi only reviews: every PR carries the criteria table and plot inline, so a merge never needs a laptop.

## 14. New ideas

Claude may message Obi with new papers or ideas that fit the theme, one short note each: what it is, why it matters for small or local models, and the experiment it suggests. Obi picks what gets built.

## 15. Deviations and SOP updates

- **One-off deviation:** allowed, and recorded in the experiment README under `Deviations from SOP` with the reason.
- **Changing the SOP:** proposed in the project chat or a `sop/<what>` PR that edits `docs/SOP.md`, with a version bump and a changelog line. Existing experiments are brought up to date only when the change affects correctness or the pass/fail verdict.
- **Canonical copy:** `docs/SOP.md` in `tiny-inference-lab`; other topic repos copy it and note the version.

## 16. Project index

One project index (https://claude.ai/artifact/P7XWwQTBfKNhrdLJ6H6hku) lists every repo and experiment with its status, verdict, key numbers and links. Every thread updates its row when a plan is posted, an experiment finishes, or a repo goes live. When a fact is needed fast, look there first.
